**What I did:**
- Researched how GitLab pipelines are actually triggered from the Ops Portal during tenant provisioning — what kicks off each pipeline, what payload is passed, and what runs downstream once a pipeline starts. 
	  Captured findings in [[GitLab pipeline trigger + tracking]]: the two-layer split (`GitlabApi` raw client + `GitlabPipelineJob` workflow-aware base class), the two trigger paths (implicit via git push vs explicit `POST /pipelines`), how status is polled and translated into the portal's `State` enum, artifact retrieval, and resilience features (retry/backoff, dry-run mode, instrumentation).
  
- Researched how the provisioning workflow advances from one job to the next — i.e. what actually drives `CI/CD entry → Cluster → Wait for pipeline → Download kubeconfig → ...`. 
	  Captured findings in [[Job transitions]]: the singleton `TenantProvisionCoordinator` (one per workflow), the `setInterval`-driven `checkPendingJobs` polling loop, the per-job state machine (`PENDING / RUNNING / SUCCESS / SKIPPED / FAILURE`), the `previousJobRes` handoff that carries values like the commit SHA between jobs, the `isRunning` re-entrancy guard, and why the design is polling-based (durability across server restarts) rather than direct job-to-job calls.
	(_Framing this research as the lead-in to the **destruction process walkthrough** — same primitives (GitLab pipelines + Argo syncs) run in reverse, so getting the provisioning side fully mapped first_).
